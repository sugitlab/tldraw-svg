# tldraw.svg エディタ 実装設計書

作成日：2026-09-22  
対象：Cursorで実装する開発者・AIエージェント  
設計バージョン：1.0

## 1. 作るもの

tldrawで編集したホワイトボードを、`sample-file.tldraw.svg` という単一ファイルで保存・再編集できるアプリを作る。

ファイルには、一般的なSVGビューアで表示するための描画要素と、tldrawで編集を続けるためのJSONを同梱する。編集データの正本はJSONとし、保存するたびに同じJSONから表示用SVGを生成する。

利用者は、普段のSVGファイルと同じように画像として扱える。専用アプリで開くと、テキスト、付箋、図形、グループ、矢印の接続関係を保ったまま編集できる。

## 2. 決定事項と初版の範囲

| 項目 | 仕様 |
| --- | --- |
| 主な利用環境 | デスクトップブラウザ。Chromium系を優先し、Firefox・Safariではファイル入出力をフォールバックする |
| アプリ構成 | ブラウザ内で編集・ファイル生成。初版のためのバックエンドは設けない |
| 保存名 | `<任意の名前>.tldraw.svg` |
| ファイルの実体 | UTF-8のSVG。MIME typeは `image/svg+xml` |
| 編集データ | SVGの `metadata` 内に、アプリ固有の名前空間を持つ要素としてJSONを格納する |
| 保存範囲 | 文書全体。全ページ、図形、接続情報、アセット、スキーマ情報を保持する |
| 画像として見える範囲 | 保存操作を開始した時点のページ全体。画面内に見えている範囲や選択中の図形だけには限定しない |
| 読み込み時に開くページ | 保存時のプレビューページ。カメラはそのページの内容に合わせる |
| 背景 | 初版は白背景・ライトテーマ。エディタと出力で揃える |
| 画像の持ち運び | 実データをdata URLとしてJSONに含める。表示用SVGも外部画像を参照しない |
| 描画方式 | ベクター優先。表示互換性を保てない場合はPNGプレビューをSVG内に埋め込む |
| 共同編集 | 初版の対象外。文書形式は将来の同期機能と分離する |
| 任意SVGの図形への変換 | 初版の対象外。専用の編集データがあるファイルを再編集する |

上表のうち、ブラウザ構成、プレビューページ、白背景、PNGフォールバックは、この設計書で置く初版の実装方針である。ファイル形式をSVGにし、編集用JSONを直接埋め込むことが今回の中心要件となる。

### 2.1 初版で扱う編集内容

標準の選択、移動、拡大縮小、回転、複製、削除、Undo/Redoを利用する。以下の図形と情報を保存対象にする。

- 幾何図形、テキスト、付箋、フリーハンド、ハイライト、線、矢印。
- 矢印の接続先、ラベル、グループ、フレーム、親子関係、重なり順。
- 静止画像、トリミング、不透明度、ロック状態、文書に属する独自の `meta`。
- 複数ページ、ページの名前と順序。

リッチテキストはJSONの内容をそのまま保持する。表示用画像への変換でリッチテキストを平文に置換しない。

動画、外部Web埋め込み、URLから取得するブックマーク、未登録のカスタム図形は初版では扱わない。新規作成・貼り付け・ドロップの各入口で制限する。非対応の内容を含む文書の読み込み・保存では、対象を示して失敗させる。対象外の図形だけを黙って落としたファイルは作らない。

### 2.2 保存しない状態

カメラ位置、選択状態、カーソル、編集中のツール、他ユーザーのプレゼンス、Undo/Redoの履歴はファイルに含めない。読み込み後は新しい編集セッションとして開始する。ファイルへの保存と同一セッション内のUndo/Redoは別の機能として扱う。

## 3. 可逆性の定義

ここで保証するのは、ファイルを再読込したあとも、元の文書を同じ意味で編集できることである。

```text
D = 保存対象のtldraw文書snapshot
C = 可搬化処理。画像参照をファイル内で完結する形式へ揃える
E = SVGファイルへの書き出し
I = SVG内のJSONからの読み込み

同一スキーマでは C(I(E(D))) と C(D) が一致する
```

比較はJSONのオブジェクトキー順を無視する。配列順、図形ID、ページID、接続先、親子関係、重なり順、文字列、座標、画像の実データは比較対象とする。

同じ画像を指す一時的なBlob URLとdata URLの違いは、画像バイト列を同一性の基準にする。画面用の座標を画像の左上に揃える処理で、文書側の座標を書き換えない。

旧スキーマの文書は、採用SDKのmigrationを適用した後の文書と比較する。SVGのXML文字列、保存日時、カメラ状態、Undo履歴の完全一致は保証対象にしない。

### 3.1 外部のSVG編集との関係

他のアプリで描画部分だけが変更されても、専用エディタは埋め込みJSONを読む。描画部分の変更を図形へ逆変換する処理は実装しない。次に専用エディタで保存すると、描画部分はJSONから生成し直される。

SVG最適化ツールなどで編集用metadataを削除すると、画像としては表示できても、専用アプリでの再編集はできなくなる。拡張子を戻しても復元できない。

## 4. 実装基盤

### 4.1 既存コードの扱い

既存のtldraw forkがある場合は、その起動方法、パッケージ管理、UI拡張方式に合わせる。空のプロジェクトなら、React + TypeScript + Viteに `tldraw` SDKを組み込む。

公開APIで保存・読み込みを追加し、SDK本体への差分を小さく保つ。既存のエディタ操作や描画エンジンを作り直さない。SDK内部への変更が必要な場合は、変更理由と上流追従時の確認箇所をREADMEに残す。

### 4.2 バージョンとライセンス

既存リポジトリが使う版を最初に確認する。新規作成時は、着手時に確認できる安定版を選び、実際のバージョンを `package.json` とlockfileに固定する。複数の `@tldraw/*` を直接使う場合は互換性を確認する。

SDKのAPIについては、採用版の型定義、ソース、同梱ドキュメントを優先する。本書の参考API名を、存在確認せずに実装しない。

2026-09-22確認時点の現行tldraw SDKはsource-availableで、本番利用には対応するライセンスが必要となる。既存forkでは、その版に付属するライセンスも確認する。ライセンス判定の削除・無効化や著作権表示の削除は行わない。本番キーがなくても、許可される開発環境で実装・確認を進める。[S1]

ライセンスキーの受け渡し口を設ける。新規構成では `VITE_TLDRAW_LICENSE_KEY` を利用できるようにし、`.env.example` に記載する。公開キーとして扱うものであり、バックエンド用の秘密情報はクライアントへ含めない。

### 4.3 SDKとの境界

SDK固有の処理は `tldrawAdapter` に集める。

| やりたいこと | 確認する公開API・機能 |
| --- | --- |
| 文書snapshotの取得 | `getSnapshot(editor.store).document` |
| 新しいstoreへの復元 | `createTLStore` と `loadSnapshot(store, { document })` |
| SVGの生成 | `editor.getSvgElement` または `editor.getSvgString` |
| PNGの生成 | `editor.toImage` |
| 文書変更の検知 | storeのlisten機能。document scopeを監視する |
| ローカル画像の管理 | `TLAssetStore` のupload / resolve |
| UIと入出力の拡張 | 採用版のメニュー・アクション・external content handler |

snapshot、画像アセット、SVG生成には既存APIを利用できる。SVGの通常の取り込みは画像配置であるため、専用ファイルの読み込みは別経路で処理する。[S2][S3][S4][S5]

## 5. ファイル形式

### 5.1 拡張子と識別

標準ファイル名は `untitled.tldraw.svg` とする。

拡張子は利用者とファイル選択UIのための目印であり、ファイル形式の判定は中身で行う。`.svg` に改名された専用ファイルも開ける。ファイル選択ダイアログのフィルターは `.svg` と `image/svg+xml` を基本とし、複合拡張子だけのフィルターに依存しない。

保存名は末尾を一度だけ正規化する。

| 入力名 | 保存名 |
| --- | --- |
| `sample` | `sample.tldraw.svg` |
| `sample.svg` | `sample.tldraw.svg` |
| `sample.tldraw.svg` | `sample.tldraw.svg` |

OSの保存ダイアログで利用者が指定した実際の名前も尊重する。handleが指す実ファイル名を、アプリ側で変更できたように表示しない。

### 5.2 SVGの構造

以下は構造説明用のXMLである。JSON部分には実際のエディタから取得したpayloadが入る。

```xml
<?xml version="1.0" encoding="UTF-8"?>
<svg xmlns="http://www.w3.org/2000/svg"
     xmlns:td="urn:tldraw-svg:document:1"
     width="1200" height="800" viewBox="0 0 1200 800">
  <metadata id="tldraw-document">
    <td:document encoding="json" version="1">JSON_PAYLOAD</td:document>
  </metadata>
  <defs><!-- 出力に必要な定義 --></defs>
  <g id="tldraw-preview">
    <!-- 表示用のSVG要素、必要に応じてdata URLのimage要素 -->
  </g>
</svg>
```

`metadata` はSVG標準の非描画要素である。独自データを別のXML名前空間に置く。[S6]

次を固定する。

- SVG名前空間：`http://www.w3.org/2000/svg`
- 編集データの名前空間：`urn:tldraw-svg:document:1`
- root直下のmetadata ID：`tldraw-document`
- metadata直下の編集データ要素のlocalName：`document`
- encoding属性：`json`
- version属性：`1`

名前空間URIは識別子であり、ネットワークアクセス先として使わない。prefixの `td` は自由に変えられるため、読み込みではnamespace URIとlocalNameで判定する。

### 5.3 JSONの型

```ts
import { getSnapshot } from 'tldraw'

// 実際の型名・import先は採用SDK版に合わせる。
type DocumentSnapshot = ReturnType<typeof getSnapshot>['document']

type TldrawSvgPayloadV1 = {
  format: 'tldraw-svg'
  formatVersion: 1
  producer: {
    app: string
    appVersion: string
    tldrawVersion: string
  }
  preview: {
    pageId: string
    background: '#ffffff'
    padding: 32
    mode: 'svg' | 'raster'
  }
  document: DocumentSnapshot
}
```

`document` はSDKのdocument snapshot全体であり、図形配列だけに縮小しない。スキーマ情報も保持する。`session` を含むsnapshot全体を誤って格納しない。

`producer.tldrawVersion` は診断用である。文字列が一致しないだけで拒否せず、実際のスキーマの読み込み可否で判断する。外側の `formatVersion` とSDKのschema versionは独立して管理する。

文書側の `meta` はJSONデータとして保持する。未知のカスタム図形を描画可能と見なすための抜け道には使わない。

`preview.pageId` は文書内に存在するページIDでなければならない。存在しない場合は、別ページを勝手に代用して成功扱いにせず、payload不正として扱う。

### 5.4 エンコード

JSONは非圧縮のテキストとして直接格納する。初版ではpayload全体のBase64化やgzip圧縮を行わない。画像のバイナリだけはdata URLを使う。

実装ではXMLをDOMとして組み立て、編集データ要素の `textContent` に `JSON.stringify(payload)` を設定してから、`XMLSerializer` で出力する。

```ts
// 部分的な実装例。rootやmetadataの作成・検証は別途行う。
const payloadElement = xmlDocument.createElementNS(
  'urn:tldraw-svg:document:1',
  'td:document'
)
payloadElement.setAttribute('encoding', 'json')
payloadElement.setAttribute('version', '1')
payloadElement.textContent = JSON.stringify(payload)
metadataElement.appendChild(payloadElement)
```

JSONをSVG文字列へ直接連結しない。これにより、文書中の `&`、`<`、`</metadata>`、`]]>`、日本語、絵文字をXMLの構造と混同しない。読み込みでは編集データ要素の `textContent` を取り出してJSON.parseする。

CDATA方式を追加しない。文字列連結によるタグ抽出や正規表現だけのXMLパースも行わない。

### 5.5 形式の検証

次をすべて満たすものを専用ファイルと判定する。

1. 正常なXMLとして解析でき、rootがSVG名前空間の `svg` である。
2. root直下に対象metadataがちょうど1つ存在する。
3. metadata直下に対象名前空間の `document` 要素がちょうど1つ存在する。
4. encodingとversionが対応する値である。
5. JSONとして解析でき、外側のスキーマを満たす。
6. XMLのversion属性とJSONのformatVersionが一致する。
7. SDKの文書スキーマと初版の対応範囲を満たす。

編集データ要素の内部にXMLの子要素は認めない。見た目が同じでも、別の名前空間に置かれた要素は採用しない。対象IDの重複や複数payloadを許容しない。

## 6. 画像とフォント

### 6.1 編集用の画像データ

画像アセットのレコードを保存するだけでは、その参照先のファイルまで持ち運べるとは限らない。SDKのアセット参照と実データを区別する。[S4]

新規アプリでは、画像の取り込み時点でdata URLを返す `TLAssetStore` を用意する。PNG・JPEG・静止WebPを初版の対応形式とする。アニメーション画像は初版では受け付けず、黙って先頭フレームへ置換しない。

既存アプリがBlob URLやIndexedDBの参照を使う場合は、保存用snapshotの複製上で実データを解決し、data URLへ置換する。稼働中の文書レコードを書き換えるための処理にはしない。

| アセットの状態 | 保存時の扱い |
| --- | --- |
| 対応するdata URL | 内容、形式、サイズ、デコード可否を検証して保持 |
| アプリ内の一時参照 | 所有するローカルストレージから解決し、data URL化 |
| HTTP(S)など外部URL | 初版では保存を止め、画像をファイルとして取り込み直すよう案内 |
| 未完了・欠損・形式不正 | 完了待ちまたはエラー。欠けた状態で成功扱いにしない |

専用ファイルの読み込みで外部URLを自動取得しない。過去の認証Cookieや署名付きURLに依存するファイルを作らない。

全ページのアセットを対象にする。初版では未参照のアセットレコードも自動削除せず、文書snapshotを保持する。ファイルサイズ削減用のクリーンアップは別機能とする。

JSON内と表示用SVG内に同じ画像データが入ることは許容する。初版では重複排除のための独自バイナリコンテナを作らない。

### 6.2 フォント

アプリに必要なSDKのフォント・アイコンは、SDKの手順に従って同一オリジンから配信できるようにする。外部CDNに依存しない構成を基本とする。[S7]

独自フォントのアップロードは初版の対象外とする。日本語や絵文字もテキストとして編集できるようにするが、別OSでエディタを開いた際のフォールバックフォントのピクセル単位の一致までは保証しない。

保存時にはフォントと画像の読み込み完了を待ってから描画する。表示用SVGの文字再現は次節の互換性方針に従う。

## 7. 表示用SVGの生成

### 7.1 SVGとJSONの保存時点を揃える

保存時に取得した不変のsnapshotから、JSONと表示用SVGの両方を生成する。SVGの生成後に稼働中のエディタからJSONを取り直す実装は避ける。

推奨構成は、保存専用のstoreと画面外に配置した一時エディタを作り、そこへ保存対象snapshotを読み込む方式とする。エディタと同じShapeUtil、BindingUtil、migration、アセット設定を使う。

文字の計測が必要なので、一時エディタを `display: none` にしない。実寸を持つ画面外の要素に配置し、操作不可にする。生成完了または失敗後は、React root、store監視、DOM、一時URLを必ず片付ける。

### 7.2 表示範囲

保存開始時に選ばれていたページの全図形を対象にする。現在の選択範囲やズームには依存しない。ページ内のグループ、フレーム、クリッピングはSDKの描画に従う。

余白は32論理px。白背景。幅、高さ、viewBoxを明記し、CSSや親HTMLのレイアウトがなくても表示できるSVGにする。

空ページも保存できるよう、800×600の白いSVGを生成する。表示に「空のページ」などの文字は追加しない。空でもmetadataは保持する。

文書は全ページを保持するが、画像として見えるのは1ページである。これをREADMEとファイルメニューの簡単な説明に明記する。非表示ページもファイル内には含まれるため、画像だけを渡す用途には後述の「表示用SVGを書き出す」を使う。

### 7.3 初版の互換性方針

最初にSDKのSVG出力を利用する。ただし、SDKのSVG出力はHTMLを含む `foreignObject` を使う場合がある。[S3]

初版では次の順で処理する。

1. 一時エディタから通常のSVGを生成する。
2. スクリプト、イベント属性、外部参照などを含まず、対象ビューアで再現できる描画ならそのまま使う。
3. `foreignObject`、ブラウザ固有のHTML描画、フォント依存の文字表示が残る場合は、同じ一時エディタからPNGを生成する。
4. PNGをdata URLの `image` 要素として、通常のSVG rootに埋め込む。
5. そのSVGに編集用JSONを埋め込む。

初版の確実な実装では、文字をパス化できていない `text` / `tspan` もPNGフォールバックの対象にしてよい。図形だけのページはベクター出力を維持する。文字を含むページがPNGプレビューになっても、再読込後の文字はJSONから編集可能な状態に戻る。

この方式は、あらゆる拡大率でベクターとして表示することを保証するものではない。画像としての表示互換性と、編集データの復元を初版の完成条件とする。局所的なPNG化や文字のパス化は、ファイル形式を変えずに後から改善できる。

PNGフォールバックの解像度は基本2倍とし、長辺8,192pxかつ総画素数1,600万画素以内に収める。SDKの内部制限も考慮する。縮小が必要な場合は、保存前にプレビュー解像度が下がることを表示する。1論理pxあたり1px未満になる場合は保存を止め、ページ内容を分けるよう案内する。黙って読めない縮小画像を保存しない。

`preview.mode` に実際の方式を記録する。PNG化は表示用SVGだけに適用し、文書内の図形を画像1枚へ置換しない。

### 7.4 最終SVGの条件

- `foreignObject`、HTML、script、イベントハンドラ、iframeを含まない。
- 外部画像、外部フォント、外部CSS、外部の `use` 参照を必要としない。
- 内部参照の `url(#id)` や `href="#id"` は許可し、ID重複を避ける。
- data URLは検証済みの静止画像など、必要な種類に限定する。
- 表示用のSVGにあるリンクは、初版ではクリック動作を持たせない。編集用JSON内のテキストは保持する。
- 描画を成立させる要素を削除して検証を通す実装にしない。安全に出せない場合はPNG化するか、理由を示して保存を止める。

## 8. 保存処理

### 8.1 保存手順

1. 実行中の保存・読み込み処理を確認し、同一文書への同時書き込みを防ぐ。
2. 新しい保存先が必要なら、利用者のクリック直後にファイル選択APIを呼ぶ。
3. 取り込み中の画像がある場合は完了を待つ。失敗している画像があれば保存を中止する。
4. document snapshot、プレビューページID、文書revision、documentEpochをまとめて取得する。
5. snapshotを複製し、全ページのアセットを可搬化する。
6. 複製を検証し、保存専用エディタへ読み込む。
7. 同じ文書から表示用SVGを生成する。
8. payloadを作り、SVGのmetadataに埋め込む。
9. 最終的なSVGを再パースして形式・外部参照・サイズを検証する。取り出したJSONが格納予定payloadと等しいことも確認する。
10. 出力を1つのBlobにまとめ、保存先へ書き込む。
11. 書き込みが完了してから、保存先・保存済みrevision・表示中のファイル名を更新する。

新規保存ダイアログは、長い画像処理の後に呼ばない。File System Access APIのファイル選択にはユーザー操作に紐づく呼び出しが必要となる。[S8]

### 8.2 保存中の編集

snapshot取得後は利用者の編集を続けられる。保存されるのは取得したrevisionであり、その後の変更は未保存として残す。

```ts
type DocumentSession = {
  documentEpoch: number
  documentRevision: number
  savedRevision: number | null
  lastDownloadedRevision: number | null
  isSaving: boolean
}
```

revisionはdocument scopeの変更で増やす。ユーザー操作だけでなく、画像取り込み完了などの文書変更も対象とする。カメラ移動や選択変更では増やさない。

新規作成・別ファイル読込時にはdocumentEpochを変える。保存開始時のepochと現在値が違う場合、古い保存処理の結果で新しい文書の表示状態を更新しない。

初版では保存・読み込み中の「開く」「新規作成」を無効にし、処理終了後に操作できるようにする。保存の連打で並列書き込みを開始しない。保存中に再度保存要求があった場合は、最新revisionの保存を1回だけ予約する。

### 8.3 保存先別の動作

File System Access APIは機能検出で使い分ける。ブラウザ名から対応を推測しない。新規構成はlocalhostまたはHTTPSで起動し、secure contextや権限などの利用条件を満たさない場合はダウンロード方式に切り替える。

| 方法 | 振る舞い |
| --- | --- |
| File System Access APIで新規保存 | 選択したhandleへwriteし、close完了後に保存成功とする |
| 同じhandleへの上書き | 権限と外部変更を確認してから上書きする |
| APIがないブラウザ | Blob URLとdownload属性でダウンロードを開始する |
| ファイル選択のキャンセル | エラー通知を出さず、文書・保存先・dirty状態を保つ |
| 書き込み失敗 | 保存成功にしない。編集中の内容を残す |

ダウンロード方式では、ブラウザがディスクへ保存したことまでは確認できない。「保存しました」ではなく「ダウンロードを開始しました」と表示する。`lastDownloadedRevision` を記録し、書き込み確認済みの `savedRevision` と区別する。未保存の保護は維持する。

作成したBlob URLは使用直後に早すぎるrevokeをせず、ダウンロード開始に必要な時間を確保して解放する。handleを取得できない通常のファイル入力から開いた場合は、元ファイルへ上書きできると見なさない。

ファイル書き込みは、出力Blobの生成と検証が完了してから開始する。streamを開いた後に失敗した場合は、利用可能な中断APIで閉じる。成功時も例外時も、書き込みstreamを開いたままにしない。

### 8.4 他アプリによるファイル変更

handle経由で開いた・保存したファイルは、その時点のバイト列のSHA-256を保存する。次の上書き前に再読込して比較する。

内容が変わっていた場合は、そのまま上書きしない。「別名で保存」と「キャンセル」を提示する。初版では自動マージや強制上書きを実装しない。

この比較は外部変更の検知であり、署名や改ざん防止の仕組みではない。ブラウザAPIにより、比較と書き込みを他プロセスに対して完全に一体化できるわけではない。

## 9. 読み込み処理

### 9.1 読み込み手順

1. ファイルサイズを確認し、UTF-8として読む。UTF-8 BOMは許容する。
2. ネットワークアクセスを行わないXMLパーサーで解析する。DOCTYPEや外部エンティティを含む入力は拒否する。
3. 第5節に従って編集用metadataを識別し、JSONを抽出する。
4. 外側のスキーマ、formatVersion、サイズ上限、対応図形・アセット、アセット参照を検証する。
5. 新しい一時storeを作り、SDKのmigrationと検証を経てsnapshotを読み込む。
6. 移行後にもアセット・対応範囲・レコード間の参照を検証する。非同期の画像検証もこの段階で終える。
7. 現在の文書に未保存変更があれば、保存・破棄・キャンセルを選べるようにする。保存を選んだ場合は保存処理の結果を待つ。
8. 成功した新storeへ切り替える。旧storeとのレコードの混在を防ぐ。
9. `preview.pageId` のページを開き、内容が見えるようカメラを合わせる。空なら初期カメラとする。
10. ファイル名・handle・元ファイルのハッシュ・revision基準を設定する。

候補ファイルの検証が失敗した時点では、表示中の文書・選択状態・Undo履歴・保存先を変更しない。先に現在のstoreをclearしてから解析する実装は禁止する。

読み込みUIは初版では編集操作を一時的に止める。成功・キャンセル・失敗のいずれでもロックを解除する。

### 9.2 読み込み内容は画面へ挿入しない

SVGの描画部分は専用ファイルの復元には不要なので、DOMやiframeへ挿入しない。編集画面は検証済みJSONから新しく描画する。

`innerHTML` や `dangerouslySetInnerHTML` で入力SVGを表示しない。読込ファイル内のSVG要素に外部参照やスクリプトが含まれていても、それを実行・取得しない。

読み込みでは描画部分が他アプリに書き換えられていても、正しい編集用JSONがあればJSONを正本として扱う。保存時の出力検証と、読み込み時のmetadata抽出を混同しない。

### 9.3 ファイルの分類

| ファイルの状態 | 動作 |
| --- | --- |
| 正常な専用ファイル | JSONから編集可能な文書を復元 |
| 拡張子が `.svg` だが正常な専用データを持つ | 同様に復元 |
| 通常SVGで編集データがない | 「このSVGには編集データがありません」と表示し、文書としての読込は行わない |
| `.tldraw.svg` だがmetadataがない・壊れている | 「編集データを読み取れません」と表示。自動で画像として追加しない |
| 未対応のformatVersion | 必要な形式バージョンを表示して読込を中止 |
| SDK側で移行できないschema | 編集データは削らず、非対応として中止 |
| 未登録・非対応の図形が含まれる | 対象の種類を表示して中止 |

通常SVGを画像として取り込む機能は、文書の「開く」と別の機能として扱う。初版ではPNG・JPEG・静止WebPの画像取り込みを必須とし、通常SVGの画像取り込みは必須にしない。

### 9.4 ドロップ・貼り付け

専用ファイルをドロップしたら、通常の画像取り込みより先に専用ファイルの判定を行い、「開く」と同じ処理へ渡す。画像アセットとして丸ごと配置しない。

PNG・JPEG・静止WebPの画像ドロップと貼り付けは、対応する画像取り込みへ渡す。URL貼り付けによるブックマークや外部埋め込みは無効にし、必要なら通常テキストとして扱う。

複数の専用文書ファイルが同時に渡された場合、初版では1ファイルずつ開くよう案内する。先頭以外を黙って無視しない。

## 10. UIと文書状態

### 10.1 ファイル操作

既存のtldrawのメニューに次の項目を追加・置換する。元のメニューと重複して異なる保存形式が並ぶ状態にしない。

| 操作 | キー | 動作 |
| --- | --- | --- |
| 新規作成 | メニューのみ | 空の文書を開く。未保存保護を行う |
| 開く | Ctrl/Cmd + O | 専用ファイルを開く |
| 保存 | Ctrl/Cmd + S | 専用ファイルとして保存 |
| 名前を付けて保存 | Ctrl/Cmd + Shift + S | 新しい保存先を選ぶ |
| 表示用SVGを書き出す | メニューのみ | 現在ページの画像だけを書き出す。編集用metadataを含めない |

ショートカットはブラウザ標準の保存画面と競合させない。メニューとキー操作は同じコマンドを呼ぶ。

表示用SVGは `sample.svg` とし、専用文書のファイル名・handle・保存済みrevisionを変更しない。これは元のSVG出力を、専用文書保存と明確に使い分けるための機能である。

### 10.2 状態表示

ファイル名、未保存変更の有無、保存中、保存失敗を簡潔に表示する。

保存成功は、実際に書き込めたrevisionに対してのみ表示する。その後の変更があるなら未保存表示を残す。ダウンロード方式は「ダウンロード開始済み」と表示して、書き込み成功と区別する。

入力ファイルの検証に失敗しても、元の文書は操作を続けられるようにする。

### 10.3 未保存保護と復旧

文書を破棄する操作では未保存変更を確認する。ネイティブ保存ができない環境では、ダウンロード開始だけを根拠に文書を自動破棄しない。ダウンロード後に利用者が破棄して続けることを選べるようにする。

ページ離脱にはブラウザ標準のbeforeunloadを利用する。独自文言が表示できる前提を置かない。

クラッシュや再読込からの復旧用に、文書snapshotをIndexedDBへ約1秒のdebounceで保存する。これはSVGファイルへの保存とは別であり、復旧保存の成功でdirtyを消さない。

復旧レコードにも、再起動後に解決できる画像実データを含める。一時的なBlob URLだけを保存しない。非同期の復旧保存を直列化し、古いrevisionの処理完了が新しい復旧内容を上書きしないようにする。

文書ごと・タブごとに識別子を割り当てる。1つの固定 `persistenceKey` を全ファイルで共有して、別ファイルや別タブの内容を混ぜない。初版では独自の小さな復旧レコードを保存し、ファイルhandleの自動復旧・自動上書きは行わない。

復旧時は「未保存の内容を復元する／破棄する」を選べるようにする。復元した文書は未保存として扱う。IndexedDBの容量不足でも、編集中の文書を失わせず、手動保存は続けられるようにする。

## 11. 検証と上限

初版の上限は定数として管理し、画面ごとに値を分散させない。

| 項目 | 初期値 |
| --- | --- |
| 入出力ファイルサイズ | 50 MiB |
| 画像1件の圧縮済みバイト数 | 8 MiB |
| 文書内の画像バイト数合計 | 16 MiB |
| 画像1件の展開後画素数 | 1,600万画素 |
| 文書内の図形数 | 10,000 |
| ページ数 | 50 |
| JSON・XMLの許容ネスト深さ | 128 |

ファイルの上限は実際の最終バイト列で判定する。JSONとSVGに同じ画像を格納した結果、アセット上限内でもファイル上限を超えることがある。

検証対象はファイルの宣言値だけに頼らず、実データから確認する。画像は拡張子とMIME typeだけで受け入れず、対応形式か・正しくデコードできるか・過大な寸法でないかを確認する。

SDKの型検証に加え、ページ・親子・binding・assetIdの参照整合性を確認する。旧形式に対して最新のレコード構造を先に押し付けず、migrationの前後で役割を分ける。正当な文書を勝手に修復・削除して成功扱いにしない。

ユーザー文書のpropsやmetaを、アプリ設定オブジェクトへ無検証にdeep mergeしない。JSONはデータとして扱う。

### 12.1 中心となる処理の契約

以下はアプリ側のインターフェース案であり、SDKに同名のAPIがあるという意味ではない。

```ts
type PortableDocument = DocumentSnapshot

type PreviewResult = {
  svg: SVGSVGElement
  mode: 'svg' | 'raster'
  pageId: string
}

type WriteResult =
  | { kind: 'written'; fileName: string; contentHash: string }
  | { kind: 'download-started'; fileName: string }
  | { kind: 'cancelled' }

async function makePortable(
  snapshot: DocumentSnapshot,
  signal: AbortSignal
): Promise<PortableDocument>

async function renderPreview(
  snapshot: PortableDocument,
  pageId: string,
  signal: AbortSignal
): Promise<PreviewResult>

function encodeEditableSvg(
  preview: PreviewResult,
  payload: TldrawSvgPayloadV1
): Blob

async function decodeEditableSvg(
  file: File,
  signal: AbortSignal
): Promise<TldrawSvgPayloadV1>
```

`encodeEditableSvg` は渡されたSVG要素を直接破壊せず、複製を使う。`makePortable` も元snapshotを変更しない。キャンセル時・例外時のリソース解放は各責務の所有者が行う。

## 13. テストと受け入れ条件

形式の読み書きが往復できるだけでは完成にしない。再編集できること、別環境で表示できること、失敗しても元の文書を失わないことを確認する。

### 13.1 codecとデータ復元

| ID | ケース | 合格条件 |
| --- | --- | --- |
| D01 | 基本的な図形を保存・再読込 | document snapshotが第3節の基準で一致する |
| D02 | 日本語、絵文字、改行、`& < >`、`</metadata>`、`]]>` | 文字列が欠けず、XML構造を壊さずに復元できる |
| D03 | 図形に接続した矢印 | 読込後に図形を移動すると矢印が追従する |
| D04 | グループ・フレーム・回転・重なり順 | 見た目と編集時の親子関係を維持する |
| D05 | 画像とトリミング | 元のアセット参照、画像バイト列、トリミングを保持する |
| D06 | 複数ページ | 全ページを保持し、保存時のページがプレビューとして表示される |
| D07 | 空ページ・空文書 | 保存、画像表示、再読込を行える |
| D08 | 続けて5回保存・再読込 | 図形数、接続、座標、文字、画像内容が変わらない |

テスト文書は採用SDKから生成する。型アサーションで無理に通した、不完全な手書きのtldrawレコードを正常系fixtureに使わない。

### 13.2 SVGの表示互換性

| ID | ケース | 合格条件 |
| --- | --- | --- |
| V01 | 図形だけのページ | ベクター要素を含むSVGとして表示される |
| V02 | 日本語・長文折り返し・リッチテキスト | 文字が欠けずに表示される。必要ならPNGフォールバックする |
| V03 | 画像・フレーム・矢印ラベル・回転を含むページ | 欠落、切れ、二重描画、背景の変化がない |
| V04 | 外部接続を遮断した環境でファイルを表示 | 画像・文字の表示に外部リソース取得を必要としない |
| V05 | metadataを除去した表示用SVG | 同じ見た目になる。専用エディタでは再編集不可として分類される |
| V06 | `.tldraw.svg` を `<img>` として表示 | 特殊なアプリコードなしで画像になる |

PlaywrightでChromiumとFirefoxの表示を確認する。さらに、`resvg` またはInkscapeなどの非ブラウザSVGレンダラーを最低1つ使う。これはアプリが使うブラウザだけに依存した出力になっていないかを確認するためである。

同じsnapshotから得た基準画像と比較し、レイアウト、テキストの欠落、クリッピングを確認する。アンチエイリアス差を許容しつつ、画像全体の大きな差や空白出力は見逃さない。自動比較に加えて代表サンプルを目視確認する。

Safariなど実機で確認できなかった項目は未確認と記載する。「あらゆるSVGアプリで完全一致」とは報告しない。

### 13.3 失敗時と競合

| ID | ケース | 合格条件 |
| --- | --- | --- |
| F01 | 壊れたXML、JSON、metadata重複、名前空間違い | 読込を中止し、元の文書・保存先を保つ |
| F02 | 将来のformatVersion、非対応schema、未知の図形 | 内容を削らずに中止する |
| F03 | 欠損画像、外部URL、偽装MIME、過大画像 | ネットワーク取得や壊れた保存をせず、理由を表示する |
| F04 | script、DOCTYPE、イベント属性、外部参照を含む入力 | 読込時に実行・外部通信が起きない |
| F05 | 保存中に図形を追加・画像を更新 | 保存ファイルのSVGとJSONが同じsnapshotに対応し、その後の変更はdirtyに残る |
| F06 | ファイル選択のキャンセル、書込失敗 | 保存成功にしない。文書を残す |
| F07 | 同じファイルを外部で変更した後に保存 | 自動で上書きしない |
| F08 | 保存連打、開く操作との競合 | 並列書込や別文書への保存状態の混入が起きない |
| F09 | File System Access APIがない環境 | ダウンロードで出力でき、完了を過大に表示しない |
| F10 | 未保存の再読込、複数タブ、復旧ストレージ失敗 | 別文書を混ぜず、未保存内容を保護する |

### 13.4 完成条件

- 開発サーバーが起動し、TypeScriptチェックと本番ビルドが通る。
- 基本の編集、専用ファイルの保存・読込・別名保存が動く。
- 「図形を描く → 矢印で接続 → 日本語入力 → 画像配置 → 保存 → 再読込 → 図形移動」の操作を確認できる。
- SVG表示とJSON復元を別々に確認している。
- `.tldraw.svg` を通常の画像取り込みへ渡してしまう経路がない。
- 未達のケースを隠して合格と扱っていない。
- READMEに起動、ライセンス、ファイル形式、プレビュー範囲、ブラウザ差、既知の制限が記載されている。

## 14. 実装順序

### 第1段階：起動と保存復元の最短経路

既存構成・SDK版を確認する。エディタを起動し、snapshotからmetadata付きSVGをダウンロードして、ファイル入力から読み戻せるところまで作る。まず四角、矢印、日本語テキストで確認する。mockのJSONでは完了としない。

### 第2段階：文書と画像を失わない保存

画像のdata URL化、全ページ保存、対応範囲の検証、XMLエスケープ、schema migration、元文書を壊さない読込を実装する。D01〜D08と入力異常系を確認する。

### 第3段階：一般SVGビューアとの互換性

保存専用エディタとPNGフォールバックを実装する。文字、日本語、フレーム、回転、画像を含む代表サンプルで、ブラウザと非ブラウザレンダラーの両方を確認する。

### 第4段階：日常のファイル操作

File System Access API、ダウンロード代替、dirty管理、保存競合、未保存保護、復旧保存、メニューとショートカットを実装する。

### 第5段階：完成確認と引き渡し

意味のある受け入れテスト、型チェック、ビルドを実行する。次のサンプルは、完成したアプリまたはその実装を使って生成する。

| ファイル | 内容 |
| --- | --- |
| `examples/basic.tldraw.svg` | 図形と接続した矢印。ベクター出力の確認用 |
| `examples/japanese-notes.tldraw.svg` | 日本語、付箋、ラベル、リッチテキスト |
| `examples/images-and-pages.tldraw.svg` | ローカル画像、トリミング、2ページ以上 |
| `examples/empty.tldraw.svg` | 空ページの保存・復元 |
| `examples/preview.png` | 代表サンプルの表示確認用画像 |

保存仕様のREADMEと検証結果を揃える。実装していない機能をTODOだけで完成扱いにしない。環境やAPIによって確認不能な項目が残る場合は、項目と理由、利用への影響を分けて報告する。

## 15. 将来拡張

初版が完成してから検討する項目をここへ分離する。

- `foreignObject`や文字部分だけを局所的にPNG化し、ベクター部分を増やす。
- 文字を適切なシェーピング処理でパス化し、日本語を含めてベクター表示する。
- 全ページを一覧画像としてSVG上に配置する出力モード。
- 対応するSVG仕様を定め、AIや他ツールが生成した図形をネイティブ図形へ変換する。
- アセットの重複排除、圧縮、文書からの未参照アセット削除。
- 独自フォント、動画、Web埋め込み、カスタム図形。
- tldraw syncによる共同編集。共同編集中の文書と、ファイル書き出し時のsnapshotを分離する。
